# The Bug Bazaar

[![CI](https://github.com/Nasir-Javed297/bug-bounty-starter/actions/workflows/ci.yml/badge.svg)](https://github.com/Nasir-Javed297/bug-bounty-starter/actions/workflows/ci.yml)

A small online store for developer gear (rubber ducks, mechanical keyboards, coffee and stickers), built with **React + TypeScript**. It runs entirely in the browser against a **mock API**, so no backend is needed.

> This repo started as the Week 1 _Bug Bounty Board_. The history is kept in Git.

## Quick start (under 5 minutes)

**You need:** [Node.js](https://nodejs.org/) **20 or newer** (`node -v` to check) and npm (comes with Node).

```bash
git clone https://github.com/Nasir-Javed297/bug-bounty-starter.git
cd bug-bounty-starter
npm install
npm run dev
```

Open the URL printed in the terminal (usually <http://localhost:5173>). That's it: the mock API starts automatically.

A `.env` file is **optional**. Every setting has a default. To change one, copy `.env.example` to `.env` and edit it (see [Environment variables](#environment-variables)).

## Mock API

The app talks to a mock backend built with [MSW](https://mswjs.io/), which intercepts `fetch` calls inside the browser. It has 5,000 seeded products and implements every endpoint in [`docs/api-contract.md`](docs/api-contract.md), including all the error codes.

- **Live stock:** the product pages open a WebSocket (`/ws/stock`, also mocked by MSW) and stock badges update without reloading. Dev tools → _Live stock: drop connections_ tests reconnection.
- **Demo account:** `demo@bugbazaar.dev` / `password123`
- **🛠 Dev tools** (bottom-right corner): switches that force errors on purpose (500, 401, 409, slow network), plus a button that resets orders and stock. The contract doc lists how to trigger [every error](docs/api-contract.md#how-to-trigger-each-error).
- Every UI state (loading, error + retry, empty, 404) can be triggered on purpose: see the table in [`docs/decisions.md`](docs/decisions.md#d2-3-ui-states).
- Don't edit `public/mockServiceWorker.js`. It's generated by MSW.

## Environment variables

Defined in `.env.example`, typed in `src/vite-env.d.ts` and read **only** in `src/config.ts`. Vite only exposes variables that start with `VITE_` to the browser, so **never put secrets here**.

| Variable            | Default | Purpose                                                                                   |
| ------------------- | ------- | ----------------------------------------------------------------------------------------- |
| `VITE_API_BASE_URL` | `/api`  | Base URL for every API request                                                            |
| `VITE_ENABLE_MOCKS` | `true`  | `true` starts the in-browser mock API (MSW). `false` turns it off (to use a real backend) |

## Folder structure

```
docs/            Written tasks: decisions, API contract, architecture...
src/
  api/           Data layer: the only code that talks to the network
  mocks/         Mock backend (MSW) for dev and tests
  store/         Redux store and slices (cart, auth)
  pages/         One component per route
  components/    Reusable UI pieces
  hooks/         Custom React hooks
  types/         Shared TypeScript types (the API contract)
  utils/         Small pure helper functions
  config.ts      Reads environment variables
  App.tsx        Header + routes
  main.tsx       Entry point: mounts React
```

## Testing

`npm test` runs **30 tests** with [Vitest](https://vitest.dev/) + [React Testing Library](https://testing-library.com/) in a simulated browser (jsdom).

- **Behaviour, not implementation:** integration tests render the whole app at a URL and use it like a shopper: find controls by their label or role, type, click, and check what's on screen.
- **Real requests:** the app's `fetch` calls go through the **same MSW handlers** as the browser mock (`msw/node`), so the data layer is tested for real.
- **Covered:** cart rules, custom hooks, filtering and URL state, login (redirect back, wrong password, double submit, 401), checkout (success, **409**, no duplicate order on retry), error mapping, UI states, the error boundary.
- Test files sit next to the code they test (`*.test.ts`); app-level tests and helpers are in `src/test/`.

## Accessibility

Lighthouse accessibility is **100** on home, cart and login (`npm run a11y`). The app works with a keyboard alone and with a screen reader: a skip link, visible focus, a title per page, focus moved to the content after navigating, labelled controls, errors in `role="alert"` regions with focus on the first invalid field, and announcements for loading and result counts. Details: [`docs/decisions.md`](docs/decisions.md#d4-1-accessibility).

## Continuous integration

Every pull request into `main` (and every push to `main` / `dev`) runs [`.github/workflows/ci.yml`](.github/workflows/ci.yml) on GitHub Actions: **type check → lint → format check → tests → build**. A branch protection rule on `main` makes this `verify` check **required**, so a pull request with a failing check **can't be merged**, not even by an admin.

## Data layer

Components never call `fetch`. Every request goes through `src/api/client.ts`, usually via the RTK Query hooks in `src/api/apiSlice.ts` (for example `useGetProductsQuery`). ESLint reports any `fetch` outside `src/api/` and `src/mocks/` as an error.

## Code quality

- **TypeScript strict mode.** `any`, `@ts-ignore` and `@ts-expect-error` are lint errors.
- **ESLint** (`eslint.config.js`) catches bugs. **Prettier** (`.prettierrc.json`) handles formatting. `eslint-config-prettier` stops the two from conflicting.
- **Line endings** are normalised to LF by `.gitattributes`, so Windows and macOS produce identical diffs.
- **VS Code:** open the folder and accept the recommended extensions. Files are then formatted and lint-fixed on save (`.vscode/settings.json`).

## Troubleshooting

| Problem                                    | Fix                                                                                                                                                                     |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run dev` says the port is in use      | Vite picks the next free port automatically. Use the URL it prints                                                                                                      |
| `node: command not found` or syntax errors | Install Node 20 or newer                                                                                                                                                |
| `npm audit` reports advisories             | They are in dev-only tooling (the Vite dev server) and don't affect the app. Don't run `npm audit fix --force`, which can upgrade Vite to an incompatible major version |
